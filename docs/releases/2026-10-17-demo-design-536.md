# Démonstration de jeu — #536

## Demande et périmètre

Le propriétaire demande une présentation plus aboutie du jeu de démonstration
et la suppression de la validation marchand introduite dans #520. Cette évolution
concerne uniquement le site public : accueil, Restaurants et Instituts de beauté.
Le retrait réel sécurisé, les modèles SaaS, API, lots et communications restent
inchangés. Aucune migration, nouvelle dépendance ou police distante ajoutée.

## Présentation

- Scène chaleureuse, téléphone mieux dessiné, identité d'enseigne et filet discret.
- Titres serif, roue ivoire/dorée ou rose à segments en dégradé, libellés contrastés.
- Contour fixe, pointeur arrondi avec liseré et ombre, centre Jouer éclairé sans icône.
- Panneaux cohérents, CTA plus lisibles, confirmation identifiée par une coche.
- Deuxième passe visuelle : centrage vertical des panneaux courts dans le téléphone.
- Suppression du composant de validation marchand, de son état/ref et CSS,
  de son bouton de confirmation et de la promesse de le tester depuis l'accueil.
- Les KPI, graphiques et synthèses de #520 sont conservés, sans incrément.

## Frontières de sécurité

Le parcours Google → rotation → formulaire → confirmation → aperçu e-mail reste
local. Aucune note ne détermine le gain illustratif. Aucun vrai PIN, code de
retrait, compte, gain, envoi, API métier ou stockage de saisie. Les champs restent
facultatifs. Les événements start/complete et leur consentement sont inchangés.
Les gradients SVG ont des identifiants propres à l'instance via useId ; seul le
rotor est animé. Le mouvement réduit, focus de chaque panneau et reset restent
pris en charge. L'avertissement de simulation reste à l'extérieur du téléphone.

## Vérification

Commandes : `npm run lint:landing`, `npm run build:landing`,
`npm run verify:source`, `npm run test:e2e -w @okado/landing-page -- --workers=3`.
Build avec la clé de mesure synthétique des tests, requêtes externes interceptées ;
aucun accès PostHog réel ni clé de production copiée.

Les E2E couvrent les trois pages à 320/390/768/1440 px, les parcours et retours,
rotation/reset, clavier, notes indépendantes, absence de validation marchand,
réseau/stockage, consentement et les preuves métier/synthèses conservées.
Le test de focus de la navigation compte les liens visibles au lieu d'imposer
six Tab : le menu Blog livré entre-temps ajoute un arrêt sur desktop. Aucun
comportement de navigation de production n'est changé par ce correctif de test.
Les captures de sections masquent seulement la navigation sticky et le bouton
fixe de cookies pendant la capture, pas dans l'application.

Le scénario visuel couvre trois parcours et les captures de chaque panneau :
son budget est de 60 s, au lieu de 30 s. Les attentes fonctionnelles ne sont pas
relâchées. Un serveur concurrent a ensuite repris le port local 3200 avec
l'ancien rendu ; les vérifications finales sont donc isolées sur le build de
cette branche : `npm run start -w @okado/landing-page -- --port 3326`, puis
`PLAYWRIGHT_BASE_URL=http://localhost:3326 npm run test:e2e -w @okado/landing-page -- --workers=3`.

Résultat final : **96 tests réussis en 4,2 minutes** sur ce serveur isolé, aux
quatre résolutions. Lint sans erreur ni avertissement, build landing et
vérification des sources réussis. Captures des six écrans inspectées ; les
contrôles de contenu vérifient les limites du téléphone et l'absence de texte
ou de contrôle débordant. Le serveur de vérification dédié est arrêté ensuite.

## Recette propriétaire

1. Accueil et Beauté : vérifier identité, titre, roue complète, pointeur et Jouer.
2. Jouer → ignorer l'avis ou essayer les étoiles → Recevoir mon gain sans saisie.
3. Vérifier la confirmation et le QR illustratif, puis Voir l'e-mail et revenir.
4. Vérifier qu'aucun bouton/étape de validation marchand n'est proposé.
5. Redémarrer pendant la rotation et depuis l'e-mail ; retrouver les champs vides.
6. Sur 320 px, vérifier textes, CTA et roue ; tester aussi au clavier.
